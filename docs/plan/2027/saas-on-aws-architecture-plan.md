# DMaker → SaaS on AWS: Architecture Plan

> **Planning-only deliverable — no code changes.** Part 1 is the plan. Part 2 (appendix) preserves the seven research reports' findings with sources.

# Part 1 — The Plan

## Context

DMaker today is a local-first, single-user "autonomous AI dev studio": a Kanban board where AI coding agents (Claude Agent SDK, plus Codex/Cursor/OpenCode/Vertex CLI providers) implement features inside isolated git worktrees on the user's machine, with live terminals (node-pty), GitHub via the `gh` CLI, JSON-file storage under `.dmaker/` + `DATA_DIR`, and an optional Electron shell. Dylan wants it to become a **multi-tenant SaaS hosted on AWS** with **every current feature working**, **Google and Microsoft as providers in both senses** (sign-in identity _and_ AI backends), **personal accounts** supported, a **correct cache strategy**, and **real tenant isolation** — designed against AWS/Azure/GCP published reference architectures.

Why this is tractable: the dev/prod pair is a working prototype of the SaaS shape. `execution-routes.ts` already classifies every "starts something" route (the control-plane/execution-plane seam), the runner daemon + `runner-client.ts` event replay is the sandbox-agent relay pattern, and `projectsRevision` is a versioned-invalidation scheme that generalizes to the whole API. What's missing is exactly what the research quantified: authentication (none exists), tenancy (the tenant key is a local filesystem path), durable scoped events, sandbox isolation (agents run `bypassPermissions` on the host), and API-based GitHub/billing/credential handling.

Two structural invariants, both industry-verified (Appendix: sandbox survey):

1. **Credentials never enter the sandbox — including AWS credentials.** LLM keys live in the gateway (sandbox holds only a run-scoped virtual key); GitHub tokens live in the git proxy (sandbox git talks to the proxy with a scoped placeholder credential; the proxy validates the operation, then attaches the real installation token — Anthropic's published pattern). Run tasks carry **no IAM task role** (at most `elasticfilesystem:ClientMount/ClientWrite` on their single EFS access point if IAM-auth mounts are used): the ECS credential endpoint (`169.254.170.2`) is served inside the task and cannot be blocked by an external egress proxy, so any role attached to the task is readable by a prompt-injected agent. All artifact I/O leaves via the dial-home channel or the proxies; STS token-vending stays in control-plane services only. This is also what makes an S3 gateway VPC endpoint safe to use (it bypasses the egress proxy — harmless only because sandboxes hold no AWS creds).
2. **All sandbox connections are outbound.** The sandbox dials home to the control plane (events, PTY frames) and out through the egress proxy (deny-all default; per-run domain allowlist; metadata endpoint + `169.254.170.2` + RFC1918 + `::ffff:`-mapped forms blocked; DNS resolve-then-pin). No inbound port is ever exposed. The dial-home WS token is **publish-only and scoped to `run/{id}`** — a sandbox can emit its own events but can never read the event bus (no cross-feature/cross-tenant read channel). Sandbox→gateway events carry seq numbers with gateway acks and a small in-sandbox retry buffer, so a gateway deploy doesn't lose events before they reach `run_events`.

### Run lifecycle (maps the current AutoModeService pipeline onto sandboxes)

1. UI/board or scheduler creates a **run** (Postgres row, FSM: `queued → provisioning → planning → awaiting_approval? → executing → pipeline_steps → build_verify → verifying → committing → done/failed/stopped`). Feature statuses keep their existing names; the run FSM is beneath them.
2. Dispatcher (SQS consumer) claims the run, checks org quotas (concurrency, budget), asks `SandboxProvider.acquire(project, runSpec)`.
3. Sandbox boots from the **project-prepared snapshot/image** (universal toolchain base + project setup layer), clones via `git clone --reference` from the project's bare-mirror cache (EFS, tenant-scoped access point), runs `.dmaker/worktree-init.sh` equivalent inside the sandbox.
4. Agent runs (Claude Agent SDK headless with `ANTHROPIC_BASE_URL=<gateway>` + run-scoped virtual key; or Codex CLI/Gemini harness likewise). Events stream out over the dial-home WS → realtime-gw → Redis → subscribed clients; also appended to `run_events` (Postgres, S3 offload for bulk).
5. Plan-approval gate, follow-ups, and chat sends re-use the same sandbox while it lives (adaptive idle timeout by tier — Fargate bills the whole idle window, so keep it short). **Suspend/resume is DIY on Fargate** (no checkpoint primitive): on teardown the run's WIP state is preserved as a WIP commit to a `refs/dmaker/run-{id}` ref via the git proxy plus a tarball of untracked files/dependency state to S3; resume provisions a fresh sandbox, restores both, and continues with `resume: sdkSessionId`. (True checkpoint/restore is exactly what the Lambda MicroVMs POC evaluates.) Concurrency: **single-writer lock per feature sandbox** — one active agent turn at a time; chat sends arriving mid-execution enter the existing per-session queue, now modeled as a visible FSM state, so two org members can't race one workspace.
6. Verify/build steps run in-sandbox; commit/PR goes through the git proxy (GitHub App token, operation-validated); run ends → sandbox destroyed (memory never reused across tenants), artifacts (agent-output.md, raw JSONL, images, diffs) persisted to S3 under the org prefix.

## Tenancy & isolation model

**Entities:** `user ─ identities (google|microsoft|email)` · `user ∈ orgs` (roles owner/admin/member/viewer; personal workspace = auto-created org, so individuals are first-class) · `org → projects (repo-connected) → features / runs / sessions / terminals`.

**Tiering (AWS bridge-model canon):** Free/Pro/Team = pooled everything. Enterprise = silo options: dedicated Postgres schema (or cluster), dedicated KMS key, reserved sandbox capacity, BYO-cloud model endpoints (Bedrock/Vertex/Foundry), later dedicated stamp.

**Isolation enforcement stack (defense in depth, every layer tenant-aware):**

1. **AuthN/Z**: Better Auth session/JWT carries `org_id` + role; every API handler resolves tenant context first; org-scoped API keys for CLI/runner.
2. **Data**: every row carries `org_id`; Postgres **RLS policies** as the second wall — set via **`SET LOCAL app.org_id` inside every transaction** (middleware-enforced), never per-connection: with transaction-mode pooling a per-connection SET leaks tenant context across requests, and under RDS Proxy it pins sessions. Pooler choice (PgBouncer transaction mode vs RDS Proxy) is made explicit with this constraint.
3. **Objects/keys**: S3 prefix-per-org accessed via **token-vending pattern** (short-lived STS creds scoped by session tags / dynamic inline policy — AWS SaaS Factory pattern); KMS envelope encryption with per-org DEKs (shared KEK pooled tiers, dedicated KMS key enterprise); BYOK provider keys sealed this way, decrypted only inside the LLM gateway.
4. **Compute**: sandbox-per-run microVM (D5/D6); run tasks carry **no AWS credentials** (invariant #1 — at most EFS ClientMount on their own access point); EFS access points per tenant; STS token-vending only in control-plane services.
5. **Network**: egress proxy policy per run; sandboxes in isolated subnets; no sandbox↔sandbox path (SG deny); control-plane services in separate SGs.
6. **Cache**: every Redis key prefixed `o:{orgId}:…`; **ElastiCache RBAC key-prefix ACLs** make the prefix an enforced boundary, not a convention. No cross-tenant derived caches — including dependency caches (npm/pnpm), which are per-tenant volumes (cache poisoning is a live attack class — TanStack incident).
7. **Fairness/noisy neighbor**: per-org concurrent-run quota by plan; weighted-fair dispatch across orgs in the scheduler; Redis token-bucket rate limits per org+user on API and WS; per-connection event throttling (already built) retained.
8. **Observability/audit**: `org_id` dimension on all logs/metrics/traces (tenant-context helper à la AWS Serverless SaaS ref arch); append-only `audit_log` per org from day one (auth events, credential changes, terminal opens, deletions).

## Identity architecture (D4 — Better Auth)

- **Google**: OIDC, scopes `openid email profile` only (non-sensitive → no verification audit); publish OAuth app to Production immediately (testing = 7-day refresh tokens); key on `sub`, treat `hd` as Workspace tenant-routing input, email = display only (Truffle-Security attack class); ONE refresh token per user (100-token cap); document our client ID + scopes for Workspace admins (they can block sign-in-only apps).
- **Microsoft**: single app registration, `signInAudience: AzureADandPersonalMicrosoftAccount`, authority `/common` (Better Auth `tenantId:'common'`); validate issuer by `tid` substitution; key users on **`(tid, oid)`** (MSA tid = `9188040d-…`); never authorize on `email` (stripped when unverified); cert/federated client creds (2-secret cap); **publisher verification early** (Partner Program + DNS domain) or risk-based step-up consent blocks us in strict tenants; support the admin-consent endpoint (tenant-ID form) for locked-down orgs.
- **Email**: password + magic link; account linking = explicit confirm flow (auto-link only on verified-email match, never for Microsoft).
- **Machine auth**: Better Auth api-key plugin → org-scoped PATs (CLI); device-authorization plugin → runner enrollment; jwt plugin JWKS → WS handshake verification.
- **Enterprise later**: SSO (SAML/OIDC) + inbound SCIM via Better Auth plugins — charge for it; no per-connection vendor tax.

## Git hosting: GitHub + GitLab, first-class (D11)

One `GitHostProvider` abstraction with two production implementations (Bitbucket/Gitea later via the same seam). Everything the product does with a repo — connect, clone/push (via the git proxy), MR/PR create+merge, issue sync/claim/labels, webhooks, new-repo detection — goes through it; no host-specific logic outside the providers.

**GitHub (as designed in D8):** GitHub App; onboarding = install app → pick org/repos (or "all repositories"); **new-repo auto-detection is native** (`installation_repositories` webhook fires when repos are added/created under an "all repos" install); short-lived installation tokens; webhook health via redelivery API.

**GitLab (mechanics finalized from the 2026-08-26 research — all tier-gating verified against docs.gitlab.com):**

- **Identity model — there is no GitHub-App equivalent**: OAuth (Authorization Code + PKCE, scopes `api read_user`) is used for **onboarding and identity only**; the durable machine credential is a **service account per customer group** (first-class bot user, free since GitLab 18.11, consumes no seat, own 2,000 req/min budget) holding a **fine-grained PAT** (GA 19.2; Repository RW + Issue/MR/Webhook CRUD) or classic-scope token on older instances, role Developer (Maintainer only where DMaker may merge protected branches).
- **Token rotation is DIY (GitLab's biggest gap vs GitHub App tokens)**: weekly cron via the rotate API (self-rotate scope — no second credential needed; rotation kills the old token instantly). Crash-safe sequence: mark rotating → rotate → verify via `GET /user` → commit; **recovery path = the connecting Owner's stored OAuth refresh token** mints a replacement (re-auth prompt if that's dead too). Alerts at 7/3/1 days via `resource_access_token_events` webhooks if rotation stalls.
- **New-repo auto-detection, per scenario**: gitlab.com **Premium/Ultimate** → one **group webhook** with `project_events` (GitLab ≥17.6) + `subgroup_events` — instant, true `installation_repositories` parity, no per-project hooks needed. gitlab.com **Free** → **polling only** (group webhooks are Premium; note the group-projects endpoint has no `updated_after` — use a `created_at` high-water mark, 60s cadence, trivially within budget) + auto-install a project webhook per discovered repo. **Self-managed** → capability-probe `GET /api/v4/version` first; Premium ≥17.6 = group hook; Free/CE = admin-installed **system hook** (`project_create`, instance-wide — filter to tenant namespaces, drop the rest) or the poller. UI shows the active detection mode ("instant" vs "60-second scan") with the Premium upsell noted.
- **Webhook reliability — GitLab never auto-retries** (open FR #355721): failed deliveries are gone; hooks auto-disable after 4 consecutive failures (permanently at 40) on gitlab.com but usually not on self-managed. Therefore the **daily reconcile poller runs on every tier**, plus a delivery-gap detector against the 7-day deliveries API with resend (5/min limit, dedupe on `Idempotency-Key`). Validation: prefer **signing tokens** (19.0+, Standard-Webhooks HMAC-SHA256 over `id.timestamp.body`), fall back to `X-Gitlab-Token` + per-tenant URL nonce; respond 200 within the 10s timeout, process async; allowlist GitLab.com egress IPs (`34.74.90.64/28`, `34.74.226.0/24`).
- **Feature-mapping deltas that change product behavior**: **multiple assignees are Premium-only** → the claim-by-assignee ownership model breaks on GitLab Free (agent would displace the human) — **claim = label** (`dmaker:claimed`; scoped `dmaker::claimed` on Premium for mutual exclusion), assignee only when tier allows or issue is unassigned; MR validation posts **commit statuses** (free, MR-widget visible) not external status checks (Ultimate); draft MR = `Draft:` title prefix; board columns stay label-mapped (free) — never depend on epics/iterations/approvals/merge trains (Premium+). Auto-merge = `PUT …/merge` with `auto_merge` + `squash`.
- **Git operations**: HTTPS with `oauth2:<token>` (OAuth, 2h — good for user-attributed ops) or token-as-password for the service account; the git proxy injects per-operation (`http.extraHeader`), commits author as the bot (clean `dmaker-agent` attribution), sandboxes hold only the proxy's short-TTL internal credential — never the real token.
- **Onboarding UX**: gitlab.com = OAuth → pick Owner-role groups → visible provisioning checklist (service account → membership → token → webhooks → initial import), degraded read-only mode + "invite an Owner" if the user lacks Owner. Self-managed = instance URL → version/capability probe rendered _before_ asking anything else → guided OAuth-app registration (paste client ID/secret — GitLab has no dynamic client registration) → same checklist (+ optional admin panel: system hook, firewall notes).
- **Connection-health UI (both hosts)**: orgs/groups connected, repo sync status, webhook delivery health + auto-disabled alarms, token expiry countdowns with rotate-now, poll freshness (Free), instance version drift warnings (self-managed re-probed weekly), API rate-limit headroom. Onboarding, managing, and detection are product surfaces, not config files.
- **Future channel noted**: GitLab's Duo Agent Platform AI Catalog now lists external agents (Claude Code, Codex CLI are launch partners) — a possible DMaker distribution path to track, not a dependency.

**Gateway verdict (D7, finalized 2026-08-26):** "Is Lite the best?" — **yes for v1, deployed with discipline.** Agent SDK → `ANTHROPIC_BASE_URL=https://gw/anthropic` (the passthrough route: body forwarded unchanged, `cache_control`/beta headers untouched, per-run virtual key as `ANTHROPIC_AUTH_TOKEN`, spend tracking + hard budgets still applied); unified `/v1/messages` translation route banned (silent `cache_control` drops shipped for months; cached-token usage still un-normalized on Bedrock/Vertex routes). Budgets: pre-call cost reservation + Redis-synced counters, worst-case drift ~10 requests — plus per-run `max_budget` + RPM caps. Ops: pin `-stable` image digests, monthly not weekly upgrades, spend-log retention hygiene. Caveats absorbed into the plan: LiteLLM's semantic cache **does not run on Anthropic-format/passthrough routes** (L2 applies to OpenAI/Gemini-format traffic only — already consistent with L2's narrow scope), and whether pre-call reservation applies with full fidelity on passthrough is empirically untested (POC item). Scale posture: Python overhead (~single-digit ms) is irrelevant next to 500ms–5s model latency; horizontal scaling is the free tier's strength; re-evaluate only past ~500–1,000 sustained RPS (LiteLLM Rust gateway → Envoy AI GW paths). Runners-up eliminated on hard requirements: Bifrost (per-replica OSS budget state "silently leaks past caps", $600-overspend report, Anthropic body conversion not passthrough), Kong (budget plugin Enterprise ~$50k/yr), Envoy AI GW (k8s-shaped, token quotas not dollar wallets), Portkey (Palo Alto acquisition overhang), Cloudflare/OpenRouter (hosted-only), Helicone (maintenance mode), thin-custom (passthrough core is 1–2 weeks; multi-replica hard budgets + per-provider streaming metering is the months-long tail LiteLLM already ships free).

### Memory / context / cache layer (lines 7, 9, 11, 12) — finalized from the SOTA research pass (2026-08-26)

Research verdict: **DMaker's existing mechanisms are already the right shapes** (ADR-style learning extraction, tiered consolidation, `masterHash` gating, tag-relevance loading = the structured-note-taking pattern Anthropic/Claude Code/Cursor all converged on). The work is porting them from files to tenant-scoped services and adding the two genuinely missing SOTA pieces. Layered design, uniform key scheme `{tenant}:{project}:{surface}:{version}:{state_fingerprint}:{content_hash}` — tenant mandatory in every key, namespace, vector index, and memory path; cross-tenant reuse default-never.

- **L0 — Provider prompt caching (now, tighten):** enforce prefix-ordering rules in every prompt builder (static system → sorted tools → context files → memory tier → append-only history → **volatile/retrieved content last** — naive RAG placement breaks prefix caching); no timestamps/UUIDs in prefixes; per-tenant cache-hit telemetry at the gateway (`cache_read_input_tokens`); OpenAI `prompt_cache_key = {tenant}:{project}:{agentKind}`; Anthropic 1h-TTL breakpoints for long runs + mid-conversation system messages (Opus 5/4.8/Fable 5) instead of prefix edits; cache-diagnostics beta when hit rates sag.
- **L1 — Exact-match `DerivedResultCache` (now, highest ROI — this is "Intent Cache"):** Valkey hot + Postgres durable (RLS); key = `sha256(task_type | prompt_version | model | normalized_inputs | state_fingerprint)` where state = commit SHA / issue hash / masterHash. Caches: project analysis, issue validations, titles/branch names/commit messages, ideation dedup, enhancement expansions, memory-tier summaries, repo maps. This is `projectsRevision` + `masterHash` promoted to a first-class service.
- **L2 — Semantic cache (later, narrow, feature-flagged):** LiteLLM `valkey-semantic` on the existing ElastiCache Valkey (valkey-search module, zero new infra) — **only** for single-shot, low-stakes, phrasing-variant calls (title/summary suggestions, duplicate-issue hints, ideation); **never** agent turns/codegen/validations (static similarity thresholds have no correctness guarantee; a key-collision attack on semantic caches is published). Threshold ≥0.9, sampled false-hit auditing, and **empirically verify the LiteLLM `namespace` partitions the vector index per tenant before launch** — if not, skip L2 (L1 captures most real duplication in a coding product). Additional constraint from the gateway verdict: LiteLLM proxy caching runs only on OpenAI-compatible surfaces, **not** on the Anthropic passthrough route — so L2 covers OpenAI/Gemini-format single-shot calls only, which is exactly its intended narrow scope.
- **L3 — Memory (port + upgrade — this is "task-intent memory" + existing learnings):** keep extraction/consolidation/tiers/hash-gating; port storage to `memories(tenant_id, project_id, scope[org|project|feature], path, frontmatter jsonb, content, embedding?, updated_at)` with RLS, markdown+frontmatter unchanged; feature-scope = episodic run/intent records (interpreted requirements, decisions — loaded for that feature's follow-ups, not globally). **Add the Mem0-style update phase** to consolidation (ADD/UPDATE/SUPERSEDE/NOOP + staleness decay — the single biggest quality upgrade; append-only memory becomes noise). **Expose via Anthropic's memory tool** (`memory_20250818`): one handler maps `/memories` → tenant/project rows (strict path validation); pair long direct-API loops with context editing + server-side compaction (Agent-SDK sessions compact themselves — don't double-manage). **Do not adopt Mem0/Zep/Letta as services** (vendor-run benchmarks unreliable; conversational-personalization strengths aren't our bottleneck).
- **L4 — Retrieval/RAG (next/later — this is lines 9/11):** **code retrieval stays agentic** (grep/glob/read in the worktree — Claude Code/Sourcegraph/Augment all found it beats embeddings for coding agents; Sourcegraph deprecated embeddings) + an Aider-style tree-sitter/PageRank **repo map** cached per commit in L1. **pgvector 0.8+ on the existing Aurora** (RLS + iterative index scans fix the multi-tenant post-filter problem) for the natural-language corpus: memories, learnings, issue/feature history, specs, docs; embeddings voyage-code-4/-3 or text-embedding-3-small (cost negligible vs LLM spend). Full code-embedding index only if a concrete feature demands it: push-webhook → Merkle/chunk-hash diff → cAST/tree-sitter chunking → embed only new hashes → S3 Vectors (GA Dec 2025, ~90% cheaper, cold-tolerant; topK≤30/no-hybrid accepted because grep remains the exact path).
- **Invalidation triggers:** git push/merge → repo-fingerprinted L1 entries + index delta; feature completion → feature caches + learning extraction; masterHash change → tier + prompt-prefix epoch; template/model change → version bump; context-file/settings edit → project prefix epoch; SUPERSEDE/DELETE → tag-relevance caches; TTL only as backstop on semantic/hot layers.
- **Build order:** now = L0 discipline + L1 + memory port + memory-tool handler; next = update phase, compaction on direct loops, pgvector corpus, repo map; later = flagged L2, push-triggered code index.

### Tenant-isolation deep-dive (how the database actually enforces it)

**Schema rules (every tenant table):**

- `org_id UUID NOT NULL` on every row; **every index leads with `org_id`** (composite `(org_id, …)`), so no query plan can efficiently cross tenants even by accident.
- **Composite foreign keys carry `org_id`** (`(org_id, feature_id) REFERENCES features(org_id, id)`) — an FK can never point into another tenant, even under an app bug.
- CI **schema lint**: a migration adding a tenant table without `org_id` + RLS policy + leading index fails the build.

**RLS as the second wall (AWS's prescribed pooled-model mechanism):**

- `ALTER TABLE … ENABLE ROW LEVEL SECURITY; ALTER TABLE … FORCE ROW LEVEL SECURITY;` (**FORCE** matters: it constrains the table owner too).
- One policy per table: `USING (org_id = current_setting('app.org_id')::uuid)` (+ identical `WITH CHECK` so writes can't cross either).
- The app connects as a **non-owner, non-superuser role** (owners/superusers bypass RLS); migrations run under a separate role.
- Tenant context: **`SET LOCAL app.org_id = $1` inside every transaction**, set by middleware from the authenticated session — never per-connection (transaction pooling would leak context; RDS Proxy would pin sessions). Pooler: PgBouncer transaction mode or the driver's pool with mandatory-transaction wrappers.
- **Verification is part of the design**: a cross-tenant fuzz suite (every API endpoint exercised with tenant-A auth against tenant-B resources must 404/403), plus a nightly RLS canary that connects as the app role and asserts zero rows visible under a random foreign `org_id`.

**Beyond rows:**

- **Per-tenant crypto**: envelope encryption — per-org DEKs under a pooled KMS KEK (enterprise: dedicated KMS key per tenant, giving cryptographic offboarding: destroy the key, the data is gone). BYOK provider keys and project secrets are sealed this way; decrypted only in the gateway/injection services. (AWS published the per-tenant data-key caching pattern Aug 2026 — 77% KMS cost reduction.)
- **Per-tenant storage access**: S3 prefix-per-org and EFS access-point-per-tenant reached only through short-lived STS credentials minted by the token-vending machine with session-tag/inline-policy scoping (AWS SaaS Factory pattern) — and only by control-plane services, never sandboxes.
- **Tenant lifecycle**: onboarding = row inserts (pooled) — no provisioning latency; offboarding = delete-by-`org_id` (partition drop where partitioned) + KMS key destruction + S3/EFS prefix deletes, executed by the audited admin console; per-tenant export (GDPR portability) via the same importer/exporter path.
- **Backup/restore**: Aurora PITR is cluster-wide; **tenant-level restore** = nightly per-org logical export (schema-filtered by `org_id`) to S3, restorable into a scratch schema without touching neighbors.

**The isolation ladder (pool → silo), per AWS bridge model / Azure tenancy models:**

1. **Pooled + RLS** (Free/Pro/Team) — Aurora Serverless v2, everything above.
2. **List-partitioned hot tenants** — largest orgs get their own partitions of the big tables (`run_events`, `messages`, `features`) for vacuum/index locality; same code.
3. **Silo schema/cluster** (Enterprise) — dedicated schema, then dedicated Aurora cluster; the storage-driver connection resolves per-org from a **tenant directory** (org → connection/shard map in the control DB). Same queries, different pool.
4. **Stamps** (P3) — whole-deployment silo per region/big customer (Azure Deployment Stamps pattern), IaC-provisioned.

**Runaway & abuse controls (a product selling compute + credits attracts both):**

- Runaway runs: token budgets alone don't stop a wedged agent burning sandbox-minutes — every run gets a **wall-clock TTL**, an FSM watchdog/reaper for stuck states, and per-org sandbox-minute caps alongside token budgets (Fargate has no built-in 8h ceiling; AgentCore/MicroVMs do).
- Abuse/fraud kit (P2 gate, before any free cloud compute): verified email **+ valid card** before sandbox access; Stripe Radar on top-ups (card-testing is a certainty); per-account velocity/concurrency caps independent of plan; egress/CPU anomaly detection for crypto-mining through allowlisted tunnels; disposable-domain signup throttling; LLM-resale detection on platform keys (per-key request-shape anomalies).

## Hybrid runner ("DMaker Connect", D3)

The existing runner, hardened and **inverted**: instead of prod pushing HTTP to `127.0.0.1:3029`, the runner **dials out** (device-code enrollment → org-scoped runner token → persistent WS to the control plane), claims jobs for projects it's authorized for, executes with the user's local tools/logins (personal subscriptions legal here), streams the same event contract back. No inbound ports, NAT-friendly. Runner auto-update keeps the exit-75/supervisor pattern.

**Security model (review-hardened — a runner is someone's personal machine):**

- **Owner-only dispatch by default.** Only the enrolling user's own actions (their runs, their chat sends) may execute on their runner; dispatching teammates' work requires an explicit per-runner org opt-in with a plain-language warning ("org members' prompts will run code on this machine"). Repo mapping alone is _not_ consent — today's `bypassPermissions` + repo-supplied `worktree-init.sh` means anyone who can write a prompt or push to the repo can execute code on the runner host.
- **Terminals and deploy scripts never relay to runners.** Interactive shells and arbitrary deploy scripts on someone else's machine are out of scope permanently; they're local-edition (own machine) or cloud-sandbox features.
- **Runner-side sandboxing before P1 GA**: drop `bypassPermissions` on runner executions (permission profile instead) and apply OS-level sandboxing for agent subprocesses (the bubblewrap/Seatbelt/WFP approach Anthropic open-sourced in sandbox-runtime) — defense for the runner owner, not just the platform.
- **No silent fallback**: the current runner-client "degrade to in-process execution" behavior is removed — in the hosted control plane that would mean executing tenant code on the API service. Runner unavailable = run fails visibly.

**Scope honesty (this is half the API surface, not just a transport flip):** today's seam deliberately keeps `/api/git`, `/api/worktree`, diffs, feature images/logs, and fs reads local because dev/prod share one disk. In P1 the control plane has no filesystem, so the runner protocol needs a **request/response RPC surface** on top of job dispatch + events: worktree/git operations (~35 endpoints), diff/status reads, attachment transfer (control plane → runner for user uploads, runner → S3 for agent-produced artifacts), and log/output retrieval. This is the bulk of P1's engineering and is estimated as such.

## Local edition: clean-repo storage + licensing (D12)

**Storage relocation (repo stays clean):** today `.dmaker/` lives inside every repo. Local mode moves all per-project data to the OS app-data area, keyed by a project registry:

- Windows: `%APPDATA%\DMaker\projects\{projectId}\` for data; `HKCU\Software\DMaker` registry keys hold the install/data-dir pointers and settings root (per Dylan's spec); `%LOCALAPPDATA%\DMaker` for caches/logs.
- macOS: `~/Library/Application Support/DMaker/…`; Linux: XDG (`~/.local/share/dmaker`, `~/.config/dmaker`, `~/.cache/dmaker`).
- The registry maps `repoPath → projectId` (with a content fingerprint so a moved repo re-links instead of duplicating). Worktrees also move out of the repo (`{appData}/DMaker/worktrees/{projectId}/…`) so `.worktrees/` stops appearing in repos.
- **Opt-in repo-committed context**: teams that _want_ shared context in git can enable a `.dmaker/context/` (or reuse `CLAUDE.md`/`AGENTS.md`) per project — explicit choice, default clean. Migration: importer detects legacy in-repo `.dmaker/`, relocates it, offers to delete the in-repo copy and add a `.gitignore` guard.
- This also fixes inventory risk-row A11 (cwd-keyed disconnect markers) and the DATA_DIR-relative-path footgun (A4) — all paths resolve through the registry, never cwd.

**Licensing (recommendation):**

- **Code**: keep the repository proprietary (all-rights-reserved or a source-available license — BUSL/FSL — if Dylan wants the code public without permitting competitors). Decision point, default = proprietary.
- **Local app**: free tier under a **proprietary EULA**, activation via DMaker account sign-in (the same Better Auth identity) so entitlements (free vs Pro features, runner enrollment) are account-based — no separate license-key infrastructure.
- **Compliance**: automated third-party license audit (node_modules NOTICE bundle shipped with the Electron build; CI license-checker gate against copyleft surprises); EULA + privacy policy shown at first run; SaaS ToS/AUP separate (trust pack).

## AWS deployment map

- **Edge**: Route53 → CloudFront (+WAF) → ALB. Webhook endpoint (github-svc) is the one unauthenticated route: `X-Hub-Signature-256` verification, dedup/replay-safe enqueue into SQS, its own WAF rate rule.
- **Services (ECS Fargate)**: `api`, `realtime-gw`, `scheduler`, `github-svc`, `llm-gateway` (LiteLLM), `git-proxy`, `egress-proxy` (per-AZ), `billing`, `admin` (internal console: org lookup, credit adjust/refund, run kill, runner de-auth, offboarding executor — audit-logged, P1). All stateless; autoscaled.
- **Data**: Aurora PostgreSQL Serverless v2 (Multi-AZ), ElastiCache Valkey, S3 (artifacts/images/events archive), EFS (**git mirrors only, Elastic throughput** — dependency caches use task-local NVMe hydrated from per-tenant S3 tarballs instead; NFS is latency-hostile for many-small-file git access, so measure and be ready to move mirrors to S3 bundles too), SQS (dispatch, webhooks), EventBridge (schedules), KMS + Secrets Manager, **SES** (magic links, verification, receipts, budget alerts — SPF/DKIM + bounce handling; P1 needs it for sign-in).
- **VPC endpoints (mandatory, not optional)**: S3 gateway endpoint (free) + ECR/CloudWatch/Secrets/STS interface endpoints — without them every multi-GB toolchain image pull and npm install transits NAT at $0.045/GB and dwarfs the infra floor at modest run volume (SOCI reduces latency, not billed bytes).
- **Execution**: dedicated ECS cluster (isolated subnets) for run tasks; **no task role** (invariant #1); SOCI lazy loading + optional warm pool for start latency; watch Fargate RunTask throttling and vCPU quotas (new accounts start low — raise proactively).
- **Observability**: OTel → CloudWatch/AMP + Grafana; `org_id` everywhere; CloudTrail; GuardDuty. **Run tasks do NOT use the awslogs driver** — agent stdout/transcripts are chatty (100–200ms event cadence) and would bill $0.50/GB ingest; events already leave via dial-home and transcripts go to S3. Trace sampling + explicit retention/log-class policy on control-plane logs.
- **Capacity management (shared upstream limits)**: platform-billed tenants share one Anthropic org's TPM/RPM — gateway does fair-share queuing + per-tenant 429s, and provider-capacity risk (the Windsurf lesson) is mitigated by multi-provider + BYO-cloud; GitHub App installation rate budgets (5k/hr-class) with per-installation backoff replace today's per-user polling; per-tenant AWS object quotas (EFS access points ~1,000/filesystem, ElastiCache ACL users, IAM roles) get sharding plans before they bite.
- **Infra cost floor (rough, corrected)**: **~$250–450/mo** at tiny scale (Aurora Multi-AZ ACUs ~$90+, Redis ~$15+, 8–9 always-on Fargate services across 2 AZs ~$120–250, NAT ~$32+data, VPC interface endpoints ~$22/AZ-set, CloudFront/S3/SES minor) + ~$0.05 sandbox cost per active run-hour + LLM tokens (dominant, passed through with margin). At 1k runs/mo compute is noise; revisit at ≥50k runs/mo (metal Firecracker path).

## Scaling & sharding strategy (incl. cache memory budget)

**Stateless tier**: every ECS service scales horizontally on CPU/latency; the WS gateway scales behind ALB (least-connections + sticky) with Redis pub/sub as the cross-instance fabric — any instance can serve any client, reconnect-resume comes from the replay ring, so gateway deploys are non-events. WS capacity planning: ~10–20k connections/instance-class; connection counts per org capped (fairness stack).

**Database scaling ladder** (matches the isolation ladder — same moves serve both): Aurora Serverless v2 ACU range (start 0.5–16, raise ceiling with load) → reader endpoints for heavy read paths (board lists, analytics) → **time-range partition `run_events`** (the one unbounded table; old partitions detach to S3 archive) and **list-partition the biggest orgs'** `features`/`messages` → silo schema/cluster per enterprise tenant via the tenant directory → directory-based horizontal sharding by `org_id` across clusters (the Azure vertically-partitioned model) if pooled ever saturates. The tenant directory (org → shard/connection) is designed in from P0 even though v1 has one shard — retrofit is the expensive part, the lookup is free.

**Sharding invariant**: `org_id` is the universal shard key — DB partitions, Redis key prefixes/ACLs, S3 prefixes, EFS access points, queue fairness, and the tenant directory all key on it, so "move a tenant" is one directory update + data copy, never a re-key.

**Queue/dispatch scaling**: SQS scales itself; the scheduler shards by org-hash if a single consumer group lags; weighted-fair dispatch guarantees no org starves another regardless of queue depth.

**Sandbox fleet scaling**: Fargate task quotas raised proactively; warm-pool size = f(P95 runs-started/min); if cold-start SLO or unit cost breaks, the SandboxProvider swap (Lambda MicroVMs / E2B-OSS on nested-virt EC2 / metal Firecracker) is the pressure valve — that's why it's an interface.

**Cache memory budget (what actually lives in RAM — ElastiCache Valkey):**

- Sessions/auth: ~1 KB/session — thousands of users ≈ MBs, noise.
- Hot entities + API-revision cache: bounded LRU, `maxmemory-policy allkeys-lru` on its logical keyspace; target ≤ 1 GB early.
- **Per-run event replay rings: the dominant item** — capped ~512 KB/run × max concurrent runs (e.g., 200 concurrent ≈ 100 MB); ring size is a hard cap, older events fall through to Postgres `run_events` (durability is the DB's job, RAM only buys resume latency).
- DerivedResultCache hot tier: ≤ 1–2 GB LRU (durable tier is Postgres; eviction only costs a DB read).
- Rate-limit/token buckets + locks: KBs.
- L2 semantic-cache vector index (if enabled): sized separately per valkey-search index; feature-flagged so it can't crowd out the operational keyspaces.
- Start on one `cache.r7g.large`-class node (or ElastiCache Serverless) ≈ 13 GB headroom vs a ≤ 4 GB working set; scale reads with replicas, scale writes with cluster-mode sharding — slots hash naturally on the `o:{orgId}:` prefix (use hash tags `{o:orgId}` so one org's keys co-locate).

## AWS research: confirmed backbone (agent report, 2026-08-26)

**What AWS's canon prescribes for exactly this product:**

- **Control plane / application plane split**, now shipped as reusable code: AWS SaaS Builder Toolkit (SBT) + three reference architectures (Serverless, EKS, ECS). Control plane = onboarding, identity, tenant config, tiering, billing/metering, per-tenant ops analytics.

- **Runtime isolation enforcement, not app-code trust**: JWT carries `tenantId` → Lambda authorizer / token-vending machine mints short-lived STS creds scoped by ABAC session tags or dynamic inline policies → Postgres RLS as the data-layer second wall → per-tenant KMS keys with encryption context for cryptographic isolation (per-tenant DEK caching pattern published Aug 2026 cuts KMS cost ~77%).
- **Untrusted agent code: never share a kernel between tenants.** AWS options, all Firecracker-derived:
  - **Bedrock AgentCore Runtime / Code Interpreter** (GA Oct 2025): dedicated microVM per session, memory-sanitized teardown, 8h max session, 15-min idle timeout, `InvokeAgentRuntimeCommand` for shell execution in the same microVM. Pricing $0.0895/vCPU-hr + $0.00945/GB-hr — **CPU billed only while actively processing; LLM-wait time unbilled** (excellent for LLM-bound agents). Caveat: session↔tenant mapping is our job.
  - **Lambda MicroVMs** (June 2026): VM-isolated sandboxes with suspend/resume + snapshot state, 8h max, auto-suspend at 15 idle minutes, explicitly marketed for "AI coding assistants that run user-supplied scripts". ~$0.10/vCPU-hr (third-party read of pricing — verify).
  - **Fargate task-per-run**: microVM per task, no shared kernel/memory/NIC — AWS's recommended strong-isolation container option. $0.04048/vCPU-hr + $0.004445/GB-hr. Cheapest managed, slower start, no suspend/resume.
  - **Self-managed Firecracker on EC2 `.metal`** (KVM needs bare metal; no nested virt on Nitro): cost floor (~$0.013/vCPU-hr on c7i.metal spot at perfect packing) but full VMM lifecycle/ops burden. The at-scale play, not the v1 play.
- **Noisy neighbor**: tier-based API Gateway usage plans + API keys, reserved concurrency per tier, tenant-tagged logs/metrics/X-Ray (tenant context helpers pattern from Serverless ref arch).
- **Multi-tenant caching**: key namespacing `tenant:{id}:…` enforced by **ElastiCache RBAC key-prefix ACLs** (per-tenant cache credentials locked to prefix on one cluster); Valkey 9.0 numbered DBs as lightweight namespaces.
- **Cost sanity, one agent-run-hour @1vCPU/2GB**: Fargate ≈ $0.049 · AgentCore ≈ $0.108 worst-case but far less when LLM-wait dominates · Lambda MicroVM ≈ $0.126 minus suspended time · metal-spot DIY ≈ $0.015.

## Sandbox execution-plane research: confirmed findings (agent report, 2026-08-26)

**How everyone builds it (the invariants — this is the actual security architecture):**

1. **VM-grade boundary per session** (Firecracker/Kata/gVisor/VM). Plain containers are never the tenant boundary; bubblewrap-style sandboxing is defense-in-depth inside the VM (Anthropic uses it that way on user machines, and still wraps cloud sessions in an isolated sandbox).
2. **Deny-all egress by default + domain-allowlist proxy**; block metadata endpoint (incl. `::ffff:169.254.169.254`), RFC1918, link-local; DNS filtering with resolve-then-pin. Codex: setup phase w/ network → agent phase network-off/allowlist. Copilot coding agent: allowlist package registries only.
3. **Gateway-side credential injection**: real credentials never enter the sandbox. Anthropic's git proxy = canonical pattern (sandbox git client uses a scoped placeholder credential; proxy validates the operation content, then attaches the real GitHub token). LLM keys likewise injected at our gateway.
4. **Snapshot-prepared environments per project** (universal toolchain image + project setup baked into a snapshot) + pause/resume for follow-up turns. Codex container caching cut p50 start 48s→5s; Cursor restores VMs from snapshots; Devin resets to clean snapshot per session. Prefer "prepared snapshot per project" over long-lived mutable volumes.
5. **Per-tenant dependency caches only** — cache poisoning is a live attack class (TanStack npm supply-chain attack came from Actions cache poisoning); restored caches are untrusted input.
6. Repo provisioning: per-project **bare mirror + `git clone --reference`** (~2s clones) + shallow/blobless partial clone into the sandbox.
7. Terminals: xterm.js ↔ WS relay ↔ PTY inside the sandbox (tmux for reattach); auth terminates at our control plane, sandbox port never exposed. Maps directly onto DMaker's node-pty TerminalService + runner event-relay shape.

**Build-vs-buy shortlist (agent's ranking, pre-AWS-constraint):**

- **A. E2B (buy)** — Firecracker, ~78ms create, pause/resume, runtime-updatable egress allow/deny, PTY streaming, **Apache-2.0 open-source infra as self-host escape hatch (Terraform/Nomad; GCP prod, AWS beta)**. Market-validated (a Devin Outposts target). ~$0.083 per 30-min 2vCPU/4GB run + $150/mo plan.
- **B. Fly Machines/Sprites** — same Firecracker boundary at 1/5–1/10 the cost; Sprites = agent-shaped lifecycle (300ms checkpoint/restore, idle = storage-only). But you build egress proxy, git proxy, snapshot pipeline yourself; young product; **not on our AWS**.
- **C. Self-managed Firecracker (defer)** — cheapest at scale; **new: EC2 nested virt on C8i/M8i/R8i (Feb 2026) removes the bare-metal requirement on AWS**; bootstrap from E2B's OSS infra when volume (≳50–100k runs/mo) or BYOC demands it.
- Cost reality: at 1,000 runs/mo every option is $8–150/mo — provider choice is a velocity/product decision until ~50–100k runs/mo. Idle-free billing (pause/suspend) matters more than headline rates for Kanban-shaped intermittent work.

**AWS-hosted reconciliation (decision for synthesis):** Dylan requires AWS hosting. AWS-native candidates from the AWS report — **Fargate task-per-run** (microVM isolation, cheap, no suspend/resume, slower start), **Lambda MicroVMs** (suspend/resume + snapshots, 8h, purpose-marketed for AI coding sandboxes), **Bedrock AgentCore** (microVM sessions, active-CPU-only billing — LLM-wait unbilled, 8h, shell-exec API) — vs **E2B self-hosted on our AWS** (beta) vs E2B cloud as off-AWS interim. ## Memory/context/cache SOTA research: confirmed findings (agent report, 2026-08-26)

**Semantic caching:** GPTCache-era static thresholds have no correctness guarantee (vCache/Berkeley: per-item learned thresholds with error bounds; a published key-collision attack exists on semantic caches).
